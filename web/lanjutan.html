Process Scheduling (CPU Scheduling)

This model uses a single CPU that executes one process at a time. When multiple processes are ready to run, the operating system must determine their order. This page simulates five scheduling algorithms for that decision.

Modify the process data, then press Run all algorithms. The program computes Gantt charts and performance metrics for each algorithm using the same data, making the comparison objective.

Processes, Threads, and Inter-Process Communication

Threads within a single process share the same memory. This makes data exchange fast, but introduces a risk: two threads can modify the same data simultaneously, corrupting the result. The following three simulations demonstrate this problem and its solutions.

A. Race Condition — why synchronization is needed

Multiple threads increment a single shared variable. The final value should be number of threads × increments per thread. Without a lock, the final value is lower because some increments overwrite each other.

Without this option, thread preemption depends on the Python scheduler so errors often do not appear, even though the code is still unsafe. Disable the option to compare results.

B. Producer – Consumer (Bounded Buffer)

The producer places items into a bounded buffer, and the consumer retrieves them. Protected by two semaphores (counting empty and filled slots) and one mutex. Note that the buffer contents never exceed the capacity, and the producer is automatically blocked when the buffer is full.

C. Dining Philosophers

Five philosophers share five forks, and each philosopher needs two forks to eat. This problem illustrates all four deadlock conditions simultaneously. Run all three strategies to compare which ones experience deadlock and which do not.

Deadlock

Deadlock occurs when a group of processes are waiting for resources held by members of the same group, so none can proceed. Four conditions must be met simultaneously (Coffman conditions): mutual exclusion, hold and wait, no preemption, and circular wait. Removing just one is sufficient to prevent deadlock.

A. Banker’s Algorithm — Avoidance

Each resource request is granted only if the system remains in a safe state afterwards, meaning there still exists an execution order that guarantees all processes can finish. A request may be denied even when the resources are available — that is its conservative nature.

Enter numbers separated by commas, one per resource type.

B. Detection & Recovery

This approach allows deadlock to occur, then detects and resolves it. For single-instance resources, deadlock is detected by finding cycles in the Wait-For Graph.

About this program

DSA Simulator is an educational simulation application for demonstrating how operating system algorithms work through verifiable numbers and steps. This application does not replace or control the computer's operating system.

Topic coverage

  1. Process Scheduling — five algorithms (FCFS, SJF, SRTF, Round Robin, Priority) compared on the same data, complete with Gantt charts and four performance measures.
  2. Process, Threads & IPC — race condition demonstrated with real threads, then fixed with mutex. Followed by two classical problems: Producer-Consumer and Dining Philosophers.
  3. Deadlock — Banker’s Algorithm for avoidance, Wait-For Graph for detection, victim termination for recovery, and Ostrich Algorithm as a comparison.

Notes about results

  • The scheduling section is deterministic: the same data always produces the same results, and correctness is tested in tests/.
  • The thread section runs real threads, so results may vary between runs. This is not a program error, but rather the nature of concurrent execution being demonstrated.
  • All numbers are computed directly by the Python program on this computer, not manually written values.
